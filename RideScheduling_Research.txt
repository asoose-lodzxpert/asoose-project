────────────────────────────────────────────────────────────────────────────────
SECTION 1 — CORE REQUIREMENTS
────────────────────────────────────────────────────────────────────────────────

WHAT A SCHEDULED RIDE ENTAILS
  • Pickup Location  — Address (lat/lng + human-readable label) chosen at booking time.
  • Drop-off Location — Same model as pickup; stored as separate Address records (matching
    the existing RidePickup / RideDropoff pattern in the Prisma schema).
  • Scheduled Date & Time — UTC-stored timestamp (scheduledAt field) with local display
    conversion on the client side.
  • Vehicle Type — Economy, Premium, SUV, etc.  Must be stored on the ride so fare
    calculation uses the correct rate card.
  • Driver Assignment — Can be deferred until N minutes before the ride; a flag
    (assignedAt) records when the driver was locked in.
  • Status lifecycle — A scheduled ride needs its own pre-ride statuses separate from the
    live-ride statuses already in RideStatus.
  • Reminders — Push and/or SMS at configurable intervals before the pickup time
    (e.g., 24 h, 1 h, 15 min).
  • Cancellation Window — Business policy that sets the latest time a customer may cancel
    without penalty (e.g., 2 hours before pickup).

BUSINESS CONSTRAINTS FOR A PRIVATE FLEET
  • Driver Roster  — The fleet has a finite driver pool; total concurrent rides are capped
    by the number of active, available drivers.
  • Max Rides / Driver / Day — Recommended ceiling: 10 rides / driver / day to manage
    fatigue; configurable via admin settings.
  • Inter-Ride Gap — Minimum buffer time between consecutive rides for the same driver
    (recommended: 30 minutes including transit back from the previous drop-off).
  • Advance Booking Window — How far into the future a customer may schedule
    (e.g., up to 30 days ahead).
  • Blackout Periods — Public holidays, maintenance windows, or driver off-days stored in
    a separate DriverUnavailability table.

RECOMMENDATIONS
  • Introduce a ScheduledRide model (or extend Ride with scheduledAt + a SCHEDULED status)
    rather than reusing the live ride flow end-to-end.
  • Store business-rule thresholds (max rides per driver, cancellation window, etc.) in the
    existing SystemSettings / admin settings pattern to allow admin-level configuration
    without code deploys.

SECTION 2 — DATABASE & DATA MODELING
────────────────────────────────────────────────────────────────────────────────

PROPOSED SCHEMA CHANGES (PostgreSQL via Prisma)

  1. Extend RideStatus enum with pre-ride states:
       SCHEDULED            — Booking confirmed, driver not yet assigned.
       DRIVER_ASSIGNED_SCHED — Driver assigned ahead of pickup time, pending acceptance.
       CANCELLED_SCHEDULED  — Cancelled before the driver was dispatched.

  2. Add fields to the Ride model:
       scheduledAt          DateTime?   — Requested pickup time (UTC).
       vehicleType          VehicleType (new enum: ECONOMY | PREMIUM | SUV | VAN)
       scheduledFare        Float?      — Pre-calculated estimate shown at booking.
       reminderSentAt       DateTime?   — Timestamp of the last reminder push.
       assignmentWindowMin  Int?        — Minutes before scheduledAt to attempt assignment.
       cancellationDeadline DateTime?   — Computed from scheduledAt minus policy window.
       isScheduled          Boolean     @default(false)

  3. New model — DriverUnavailability:
       id         String   @id @default(uuid())
       riderId    String
       startsAt   DateTime
       endsAt     DateTime
       reason     String?
       @@index([riderId, startsAt, endsAt])

  4. New model — ScheduledRideReminder (audit trail for sent reminders):
       id         String   @id @default(uuid())
       rideId     String
       channel    String   — "PUSH" | "SMS" | "EMAIL"
       sentAt     DateTime @default(now())
       minutesBefore Int
       success    Boolean  @default(true)

DRIVER AVAILABILITY QUERY PATTERN
  • To find available drivers at a given timeslot:
      SELECT * FROM riders
      WHERE id NOT IN (
        SELECT riderId FROM rides
        WHERE status IN ('SCHEDULED','IN_PROGRESS','DRIVER_ASSIGNED_SCHED')
          AND scheduledAt BETWEEN :windowStart AND :windowEnd
      )
      AND id NOT IN (
        SELECT riderId FROM driver_unavailabilities
        WHERE :requestedTime BETWEEN startsAt AND endsAt
      )
      AND isAvailable = true;

  • Add compound index: @@index([riderId, status, scheduledAt]) on Ride for fast lookups.

STATUS TRACKING FLOW
  SCHEDULED → (driver assignment window opens) → DRIVER_ASSIGNED_SCHED
            → (driver accepts) → DRIVER_ACCEPTED
            → (customer pays) → PAID
            → (driver starts trip) → IN_PROGRESS
            → COMPLETED
            Alternative exits: CANCELLED_SCHEDULED | CANCELLED_BY_USER | CANCELLED_BY_DRIVER

RECOMMENDATIONS
  • Prefer adding scheduledAt + isScheduled to the existing Ride model over a separate
    ScheduledRide table — it keeps queries unified and avoids join overhead.
  • Use partial indexes in PostgreSQL: CREATE INDEX ON rides (scheduledAt) WHERE isScheduled = true;
  • Always store scheduledAt in UTC; convert to local timezone only at the presentation layer.

SECTION 3 — DRIVER ASSIGNMENT LOGIC
────────────────────────────────────────────────────────────────────────────────

ASSIGNMENT TIMING STRATEGIES

  Strategy A — Immediate Assignment (at booking)
    • Pros: Driver knows schedule early; customer gets confirmation fast.
    • Cons: Driver may cancel between booking and ride time, requiring re-assignment.
    • Best for: Rides scheduled < 2 hours ahead.

  Strategy B — Deferred Assignment (N minutes before pickup)
    • Assign a driver 60–90 minutes before scheduledAt using a scheduled job.
    • Pros: Uses real-time availability; reduces long-lead cancellations.
    • Cons: Customer has no driver name/plate until close to pickup.
    • Best for: Rides scheduled 2+ hours ahead (recommended for this private fleet).

  Strategy C — Hybrid
    • Accept scheduling now; show "Driver will be assigned 1 hour before pickup."
    • If an admin wants to pre-assign, allow it via admin panel (manual override).

ASSIGNMENT ALGORITHM (Recommended)
  1. Get all available drivers who have no conflicting rides within
     [scheduledAt - interRideGapMin, scheduledAt + estimatedDurationMin + interRideGapMin].
  2. Score each driver by:
       - Proximity to pickup location (haversine distance; use Google Maps Distance Matrix
         API for accuracy — already integrated via MapsModule).
       - Remaining rides today vs. max-rides-per-day cap.
       - Total hours driven today (fatigue management).
       - Driver rating (optional weight).
  3. Assign the highest-scoring driver.
  4. If no driver is available: status → CANCELLED_BY_SYSTEM or admin alert.

CONFLICT / DOUBLE-BOOKING PREVENTION
  • Use a Prisma transaction + SELECT FOR UPDATE or an optimistic lock (version field) when
    assigning a driver to prevent race conditions when two rides are assigned simultaneously.
  • Alternatively, use a Redis-based distributed lock (Redlock pattern) around the
    assignment logic — Redis is already in the stack via the RedisModule.

MANUAL VS AUTOMATIC ASSIGNMENT (Private Fleet)
  • Recommend exposing both modes in the admin panel:
      - Auto-assign (default): runs the scoring algorithm.
      - Manual override: admin selects a specific driver; system validates no conflict.
  • Track assignedBy field (SYSTEM | ADMIN | userId) for audit purposes.

IMPLEMENTATION IN THIS STACK
  • Use @nestjs/schedule with a @Cron job running every 5 minutes to evaluate upcoming
    rides whose scheduledAt falls within the assignment window.
  • Alternatively (more precise): use BullMQ delayed jobs — at booking time, enqueue a
    job with a delay = scheduledAt - assignmentWindowMin; the job worker runs the
    assignment algorithm. BullMQ is already set up via QueueModule.
  • BullMQ delayed job approach is recommended — it avoids polling and is more precise.

RECOMMENDATIONS
  • Use BullMQ delayed jobs for driver assignment scheduling.
  • Default assignment window: 90 minutes before pickup.
  • Implement Redis-based Redlock to prevent double-booking on concurrent assignments.
  • Log every assignment attempt (success/failure + reason) for admin visibility.

SECTION 4 — NOTIFICATION & REMINDER SYSTEMS
────────────────────────────────────────────────────────────────────────────────

EXISTING NOTIFICATION INFRASTRUCTURE (from codebase review)
  • Expo Push Service — ExpoPushService already implemented in src/libs/expo/.
  • Firebase Cloud Messaging — FcmService already implemented in src/libs/fcm/.
  • WebSocket Gateway — NotificationsGateway sends real-time in-app notifications.
  • Both FCM tokens and Expo push tokens are stored per user (user.fcmToken,
    user.expoPushToken) — dual-channel push is already supported.

SCHEDULED RIDE NOTIFICATION EVENTS & TRIGGERS

  Event                          | Channel(s)               | Timing
  -------------------------------|--------------------------|---------------------------
  Ride booked confirmation       | Push + In-app            | Immediately at booking
  Driver assigned                | Push + In-app + SMS      | When driver is locked in
  Reminder — 24 hours before     | Push + SMS               | scheduledAt - 24h
  Reminder — 1 hour before       | Push + SMS               | scheduledAt - 60min
  Reminder — 15 minutes before   | Push                     | scheduledAt - 15min
  Driver on the way              | Push + In-app            | When driver starts moving
  Driver arrived at pickup       | Push + In-app            | Real-time (live ride flow)
  Ride cancelled                 | Push + In-app + SMS      | On cancellation event
  Admin alert — no driver found  | In-app (admin panel)     | After assignment failure

EXPO NOTIFICATIONS vs FIREBASE CLOUD MESSAGING
  • Expo Push (already in stack): Simplest for managed Expo workflow; wraps FCM/APNs.
    Suitable when both apps are built with Expo; free tier is generous.
  • FCM (already in stack): Lower-level; required for background delivery guarantees on
    Android and for web push. More reliable for critical alerts like driver assignment.
  • Recommendation: Use FCM as primary push channel for scheduled reminders (higher
    delivery reliability); use Expo Push as fallback. Current dual-channel logic in
    NotificationsService already supports this pattern.

SMS NOTIFICATIONS (Low-connectivity fallback)
  • Termii — Nigerian-focused SMS gateway; supports OTP and bulk SMS; simple REST API.
    Website: https://termii.com | Docs: https://developers.termii.com
  • Twilio — International coverage; strong SDK support; higher cost per SMS in Nigeria.
  • Recommended for Nigeria: Termii for domestic SMS, Twilio as fallback for roaming.
  • Integrate via a dedicated SmsService in src/libs/sms/ that normalises the provider
    interface so switching providers requires no changes to callers.

REMINDER SCHEDULING IMPLEMENTATION
  • At ride booking time, enqueue three BullMQ delayed jobs:
      - "ride.reminder.24h"  → delay = (scheduledAt - 24h) - now
      - "ride.reminder.1h"   → delay = (scheduledAt - 60min) - now
      - "ride.reminder.15min" → delay = (scheduledAt - 15min) - now
  • Each job reads the current ride status; if CANCELLED, it no-ops (no reminder sent).
  • Store job IDs on the ScheduledRideReminder record so they can be removed on
    cancellation via queue.remove(jobId).

RECOMMENDATIONS
  • Integrate Termii for SMS in the Nigerian market; wrap in a provider-agnostic SmsService.
  • Use BullMQ delayed jobs for all reminder scheduling — consistent with the existing
    job queue architecture.
  • On cancellation, explicitly remove pending BullMQ reminder jobs to avoid ghost messages.
  • For the driver-side app (rider-app), send a high-priority FCM data message
    (not notification) so it can wake the app for assignment alerts.

SECTION 5 — SCHEDULING & TIME MANAGEMENT
────────────────────────────────────────────────────────────────────────────────

TIME ZONE HANDLING

  Problem
  • Nigeria operates on WAT (West Africa Time = UTC+1) year-round (no DST).
  • Corporate clients or future international expansion may span multiple zones.

  Best Practices
  • Store ALL timestamps in UTC in PostgreSQL (Prisma DateTime maps to TIMESTAMPTZ).
  • Accept scheduledAt from the client as an ISO 8601 string with UTC offset or as plain
    UTC. Reject ambiguous local-time-only strings.
  • Convert to local time only in the UI layer using the device's or user-configured
    timezone. In React Native, use the `date-fns-tz` or `luxon` library.
  • For admin dashboards, expose a timezone selector; persist user timezone preference.

  Recommended Libraries
  • Backend : `date-fns` (already likely in use); add `date-fns-tz` for offset arithmetic.
  • Mobile   : `luxon` (lightweight, immutable DateTime); integrates well with Expo.
  • Avoid    : Moment.js (deprecated, large bundle).

DATE / TIME PICKER — MOBILE & WEB
  • React Native / Expo: `@react-native-community/datetimepicker` — official, cross-platform.
  • Expo-specific wrapper: `expo-datetimepicker` or third-party `react-native-modal-datetime-picker`
    (more polished UX).
  • Minimum scheduling lead time: enforce at least 30 minutes ahead on the client and
    re-validate on the server to prevent race conditions.
  • Web (customer-web-app): standard HTML `<input type="datetime-local">` + shadcn/ui
    calendar component or `react-day-picker`.

CANCELLATION & RESCHEDULING WORKFLOW

  Cancellation Rules
  • Free cancellation window: up to (scheduledAt - cancellationWindowHours) [admin-configurable].
  • Late cancellation: flag ride with lateCancellation = true; optionally apply a fee.
  • System cancellation (no driver found): always free, trigger a full refund flow.

  Rescheduling Rules
  • Allow rescheduling up to X hours before pickup (separate configurable threshold).
  • Rescheduling: update scheduledAt → re-validate driver availability → if current driver
    conflicts, release and re-assign → re-enqueue reminder jobs (cancel old ones first).
  • Limit reschedules per ride to prevent abuse (e.g., max 2 reschedules).

  Implementation
  • PATCH /rides/:id/schedule endpoint accepts a new scheduledAt.
  • Wrap in a database transaction: update ride, release driver if conflicting, remove
    old BullMQ jobs, enqueue new ones.

RECOMMENDATIONS
  • Mandate UTC storage; never store local time in the database.
  • Use `luxon` on mobile clients for reliable timezone-aware datetime formatting.
  • Expose cancellation and rescheduling policies as admin-configurable settings
    (cancellationWindowHours, maxReschedules, rescheduleWindowHours).
  • Add server-side validation for minimum advance booking (30 min) and maximum horizon
    (30 days) to guard against invalid bookings.

DRIVER APP (RIDER-APP) INTERFACE

  Upcoming Rides List

    • Quick toggle for "Mark as Unavailable" (creates a DriverUnavailability record).

ADMIN PANEL PATTERNS

  • Driver workload heatmap: rides per driver per day.
  • Manual assignment modal: select driver → system shows conflict warnings in real time.
  • Alert list for rides with no driver found.

SECTION 8 — EDGE CASES & FAILURE HANDLING
────────────────────────────────────────────────────────────────────────────────

NO DRIVERS AVAILABLE AT ASSIGNMENT TIME
  • Status → CANCELLED_BY_SYSTEM; trigger full refund.
  • Notify customer with reason ("No available driver for your scheduled time").
  • Alert admin panel with the ride ID for manual intervention.
  • Optional: Allow the customer to reschedule rather than auto-cancel; offer alternative
    time slots based on driver availability query.
  • Retry strategy: attempt assignment at T-90min; if no driver, retry at T-60min and
    T-30min before cancelling the ride.

RIDE CANCELLATIONS OR CHANGES
  • Customer cancels after free window → apply late cancellation fee; partial refund.
  • Driver cancels a scheduled ride → immediate re-assignment attempt; push alert to
    customer ("Finding you a new driver").
  • If re-assignment fails → CANCELLED_BY_SYSTEM; full refund; priority bump for
    customer's next booking (loyalty gesture).
  • On every cancellation: cancel pending BullMQ reminder jobs using their stored job IDs.

LATE DRIVERS OR NO-SHOWS
  • If driver does not start trip within X minutes after scheduledAt (configurable,
    default 10 min): system sends escalation alert to admin.
  • At T+15 min no-show: auto-cancel the ride; treat as driver cancellation; refund
    customer; flag rider for review.
  • Expose "Driver Late" report button in customer app for manual reporting.

OVERLAPPING / CONFLICTING SCHEDULES
  • Prevent at assignment time via the availability query (see Section 3).
  • Add a database-level unique constraint or CHECK constraint:
    no two active rides for the same riderId overlap in time.
  • Use optimistic locking (version field on Ride) to detect concurrent assignments.

DOUBLE-BOOKING
  • Risk: two concurrent booking requests assigned the same driver simultaneously.
  • Mitigation: Redlock distributed lock on `driver:{riderId}:assignment` key;
    TTL = 5 seconds; acquire before writing, release after commit.

REMINDER JOB FAILURES
  • BullMQ retry policy: maxAttempts = 3, backoff = exponential (2s, 4s, 8s).
  • On final failure: log to ScheduledRideReminder with success = false for auditing.
  • Do NOT crash the job worker on push notification failures (Expo push can throttle);
    swallow the error, log, and rely on the next reminder interval.

PAYMENT FAILURES ON SCHEDULED RIDES
  • Recommended flow: pre-authorise the fare at booking; capture at ride start.
  • If pre-auth fails at booking → reject the schedule request.
  • If capture fails at ride start → halt the ride and notify both parties.

DATABASE TIMEZONE MISMATCH
  • Risk: scheduledAt stored as local time accidentally leads to incorrect reminder timing.
  • Mitigation: enforce UTC at the DTO validation layer (use `@IsISO8601()` + server-side
    `new Date(dto.scheduledAt)` which normalises to UTC).

RECOMMENDATIONS
  • Implement a scheduled ride health-check @Cron job (every 5 minutes) that:
    - Flags rides still in SCHEDULED status with scheduledAt in the past.
    - Triggers admin alerts for stuck rides.
  • Build an admin "Emergency Assign" endpoint for manual intervention when all retries fail.
  • Log all notification send attempts (success, failure, channel) for SLA auditing.

SECTION 9 — COMPETITOR RESEARCH
────────────────────────────────────────────────────────────────────────────────

BOLT FOR BUSINESS (NIGERIAN MARKET)
  Patterns Identified:
  • Allows scheduling up to 7 days in advance via the Bolt Business app.
  • Uses a "10-minute pre-trip" driver dispatch model (assigns driver very close to
    pickup time to maximise driver availability and minimise wait).
  • Sends push + email reminders; no SMS by default.
  • Corporate accounts get a dashboard showing all employees' scheduled trips.
  Pitfalls:
  • Driver assignment this late (10 min) sometimes fails in low-supply areas of Lagos/Abuja.
  • No offline/SMS fallback for areas with poor connectivity.

INRIDE (NIGERIA)
  Patterns Identified:
  • Operates a private fleet model similar to the target app.
  • Uses manual driver assignment by a dispatcher via WhatsApp coordination — inefficient
    but culturally familiar to Nigerian drivers.
  • SMS receipt sent to customer at booking confirmation — popular because data is
    unreliable in some corridors.
  Pitfalls:
  • Manual dispatch is not scalable beyond ~20 drivers.
  • No automated reminders; relies on dispatcher memory.

LOCAL NIGERIAN TAXI FLEETS (INFORMAL SECTOR)
  Patterns Identified:
  • Booking via phone call or WhatsApp; dispatcher logs rides in a spreadsheet.
  • Driver briefed via WhatsApp group message.
  • Common time buffer: 30 minutes between rides, managed manually.
  Pitfalls:
  • No real-time tracking, no cancellation policy, frequent double-bookings.
  • Total dependence on dispatcher availability.

SMS-BASED SCHEDULING SYSTEMS (FEATURE-PHONE MARKETS)
  Patterns Identified:
  • USSD or SMS keywords (e.g., "BOOK [date] [time] [pickup] [dropoff]").
  • Used in rural and peri-urban areas; driver contacts customer directly by phone.
  • No app required — works on any handset.
  Pitfalls:
  • Very limited data capture; no real-time updates.
  • Hard to enforce cancellation policies.

COMMON PATTERNS ACROSS COMPETITORS
  • Confirmation at booking (push/SMS/email) is universally expected.
  • Customers prefer knowing the driver's name and estimated arrival time as early as possible.
  • Corporate clients expect a consolidated booking history and invoice export.
  • SMS fallback is a differentiator in the Nigerian market and helps with driver-facing
    alerts when internet connectivity is intermittent.

PITFALLS TO AVOID
  • Last-minute (< 10 min) driver assignment in a private fleet creates unacceptable
    risk of ride failure — use 60–90 min window instead.
  • Building a rigid scheduler without admin override capability makes operations brittle.
  • Ignoring offline scenarios: drivers in some parts of Nigeria rely on SMS because
    mobile data is expensive or unavailable on the route.
  • Forgetting to cancel BullMQ jobs on rescheduling/cancellation leads to ghost
    notifications that erode user trust.

RECOMMENDATIONS
  • Differentiate from Bolt Business by offering a longer scheduling horizon (up to 14–30
    days) and a confirmed driver assignment 60–90 minutes before pickup.
  • Invest in SMS notifications as a first-class channel — Termii makes this inexpensive
    in Nigeria.
  • Offer a super-admin dispatcher view to allow manual coordination similar to what
    informal fleets use, bridging the gap between tech and ops culture.
  • Consider a WhatsApp Business API integration (via Twilio or 360dialog) as a
    notification channel — WhatsApp penetration among Nigerian drivers is near universal.

SECTION 10 — RIDE DURATION ESTIMATION (RECOMMENDED IMPROVEMENT)
────────────────────────────────────────────────────────────────────────────────

WHY DURATION ESTIMATION IS REQUIRED
  Driver availability is not just about a point in time — it spans a window.
  Without knowing how long a ride will take, it is impossible to determine whether
  a driver is truly free for a new booking.

  Example conflict without duration awareness:
    Ride 1 : scheduledAt = 9:00 AM,  estimatedEndTime = 9:40 AM
    Ride 2 : scheduledAt = 9:20 AM
    → Driver cannot accept Ride 2 even though 9:20 AM looks "free" on paper.

  Currently the Ride model stores durationMin (actual, recorded after completion) but
  has no pre-trip estimated duration at scheduling time. This gap must be filled.

PROPOSED SCHEMA ADDITIONS TO THE RIDE MODEL
  estimatedDurationMin  Int?      — Estimated trip duration in minutes (computed at booking).
  estimatedEndTime      DateTime? — scheduledAt + estimatedDurationMin; used for conflict checks.

  Both fields are nullable so they remain optional for live (on-demand) rides.

HOW TO COMPUTE estimatedDurationMin
  • Call the Google Maps Directions API (already available via MapsModule) at booking time
    with the pickup and drop-off coordinates and the expected departure time (scheduledAt).
  • The API returns duration_in_traffic — the most accurate estimate for a given time
    of day and day of week.
  • Add a configurable buffer (default: 15 minutes) for post-drop-off driver turnover
    before the next ride window opens.
  • Formula:
      estimatedEndTime = scheduledAt + estimatedDurationMin + interRideGapMin

UPDATED DRIVER AVAILABILITY QUERY
  A driver is available for a new ride at [scheduledAt, estimatedEndTime] only if:

    No existing ride for that driver satisfies:
      existing.scheduledAt < new.estimatedEndTime
      AND existing.estimatedEndTime > new.scheduledAt

  This is a standard interval-overlap check:
    NOT (existingStart >= newEnd OR existingEnd <= newStart)

  SQL equivalent:
    SELECT * FROM rides
    WHERE riderId = :driverId
      AND status IN ('SCHEDULED', 'DRIVER_ASSIGNED_SCHED', 'IN_PROGRESS')
      AND scheduledAt    < :newEstimatedEndTime
      AND estimatedEndTime > :newScheduledAt;

  If this returns any rows → driver is busy; skip them in the assignment algorithm.

IMPACT ON ASSIGNMENT ALGORITHM (Section 3 UPDATE)
  • Step 1 of the scoring algorithm must now apply the interval-overlap check instead
    of a simple point-in-time check.
  • estimatedEndTime should be indexed: @@index([riderId, scheduledAt, estimatedEndTime]).
  • If Google Maps API is unavailable at booking time: fall back to a distance-based
    heuristic (distanceKm / averageSpeedKmh * 60) and flag the ride for re-estimation
    when the API recovers.

RECOMMENDATIONS
  • Always call the Directions API at scheduling time and store estimatedDurationMin
    and estimatedEndTime on the Ride record.
  • Re-estimate on rescheduling (scheduledAt change invalidates the previous estimate).
  • Display estimatedEndTime to the driver in the upcoming-rides list so they can plan
    their day accurately.
  • Add a @@index([riderId, scheduledAt, estimatedEndTime]) compound index for
    fast overlap queries across a driver's schedule.


────────────────────────────────────────────────────────────────────────────────
SECTION 11 — DRIVER WORKING HOURS / SHIFT MANAGEMENT (MISSING FEATURE)
────────────────────────────────────────────────────────────────────────────────

WHY THIS WAS MISSING — AND WHY IT MATTERS
  The earlier sections handle real-time conflicts between rides but do not account for
  when a driver is actually allowed to work. Without shift management, the assignment
  algorithm could legitimately assign a driver to a 2:00 AM ride, violating safety
  regulations, driver contracts, and company policy.

  Example:
    Driver shift : 8:00 AM → 6:00 PM
    Scheduled ride : 5:45 AM
    → Without shift enforcement, the algorithm may assign this driver.
    → With shift enforcement, the ride is correctly rejected or escalated to admin.

PROPOSED NEW MODEL — DriverShift

  model DriverShift {
    id          String   @id @default(uuid())
    riderId     String
    dayOfWeek   Int?     — 0 (Sun) – 6 (Sat); null = applies every day
    startTime   String   — "HH:MM" in 24-hour format (WAT local time)
    endTime     String   — "HH:MM" in 24-hour format (WAT local time)
    isActive    Boolean  @default(true)
    createdAt   DateTime @default(now())
    updatedAt   DateTime @updatedAt

    rider Rider @relation(fields: [riderId], references: [id], onDelete: Cascade)
    @@index([riderId, dayOfWeek])
  }

  Notes:
  • startTime / endTime stored as "HH:MM" strings allow simple comparison without
    timezone complexities (shift times are inherently local working-hours concepts).
  • dayOfWeek = null means the shift repeats every day of the week.
  • Multiple rows per driver support different shifts on different days
    (e.g., Mon–Fri: 8AM–6PM, Sat: 9AM–3PM, Sun: off).

SHIFT ENFORCEMENT IN THE ASSIGNMENT ALGORITHM
  Before assigning a driver, check:
    1. Retrieve the driver's DriverShift for the day of week of scheduledAt.
    2. Convert scheduledAt to WAT local time.
    3. Verify: shiftStart ≤ scheduledAt_local AND estimatedEndTime_local ≤ shiftEnd.
    4. If the ride falls outside the shift window → exclude the driver.

  Edge case — rides that cross midnight:
    If a shift is 10:00 PM – 6:00 AM (night shift), endTime < startTime.
    Handle by checking: scheduledAt_local >= startTime OR estimatedEndTime_local <= endTime.

DRIVER UNAVAILABILITY VS DRIVER SHIFT
  • DriverShift  — Recurring structured availability (weekly pattern).
  • DriverUnavailability (Section 2) — One-off overrides: sick day, leave, maintenance.
  • The assignment query must exclude drivers who fail EITHER check.

ADMIN MANAGEMENT OF SHIFTS
  • Admin panel: per-driver shift editor with a weekly calendar grid.
  • Allow bulk assignment of a standard shift template to multiple drivers.
  • Show warnings when a driver has rides scheduled outside their defined shift.
  • Expose a "Shift Coverage" report: which hours of the day have no drivers available.

DRIVER-FACING SHIFT VISIBILITY
  • Show drivers their current shift in the rider-app home screen.
  • "Mark as Unavailable" toggle (Section 6) creates a DriverUnavailability record and
    should prompt: "This will affect X upcoming scheduled rides. Continue?"

RECOMMENDATIONS
  • Implement DriverShift as a first-class model before enabling public ride scheduling;
    without it, the fleet is exposed to unsafe or unsatisfied assignments.
  • Default all new drivers to a standard shift (e.g., 7:00 AM – 9:00 PM) so they are
    not inadvertently scheduled outside working hours while their custom shift is pending.
  • Validate shift conflicts at ride-assignment time server-side; never trust the client.
  • Store shift times as WAT-local "HH:MM" strings and convert to UTC only for overlap
    arithmetic, keeping the mental model simple for dispatchers.

SECTION 12 — OPERATIONS DASHBOARD (FEATURE FOR DAY-TO-DAY MANAGEMENT)
────────────────────────────────────────────────────────────────────────────────

WHY AN OPERATIONS DASHBOARD IS ESSENTIAL
  Automation handles the majority of assignment and reminder work, but automation is
  never perfect. Dispatch operators need a real-time view to:
    • Catch rides that failed auto-assignment before the customer notices.
    • Intervene when a driver cancels close to pickup time.
    • Balance driver workload across the fleet.
    • Audit the day's performance (on-time, late, cancelled).

  Without this dashboard, operators are flying blind and will default to managing
  via WhatsApp — unscalable beyond a small fleet.

DASHBOARD PANELS & FEATURES

  1. TODAY'S SCHEDULED RIDES PANEL
     • Table/list of all rides with scheduledAt = today, sorted chronologically.
     • Columns: Ride ID | Customer | Pickup | Drop-off | Scheduled Time | Driver | Status | Actions.
     • Colour-coded status badges:
         - Blue   : SCHEDULED (no driver yet)
         - Yellow : DRIVER_ASSIGNED_SCHED (awaiting acceptance)
         - Green  : PAID / IN_PROGRESS
         - Red    : CANCELLED / CANCELLED_BY_SYSTEM
         - Orange : Stuck (scheduledAt passed, still in SCHEDULED/DRIVER_ASSIGNED_SCHED)
     • Inline "Assign Driver" button for rides in SCHEDULED status.
     • Inline "Reassign" button for rides where the driver cancelled.

  2. DRIVER STATUS PANEL
     • List of all active drivers with current status:
         On Shift | Off Shift | On a Ride | Available | Unavailable (marked off).
     • Mini timeline per driver: horizontal bar showing assigned rides for today.
     • Click-to-expand: full day schedule, gap indicators, total ride count vs. daily cap.

  3. ASSIGNMENT STATUS & FAILURE ALERTS PANEL
     • Feed of recent assignment events:
         ✅ Driver X assigned to Ride Y at 09:14 AM
         ❌ No driver found for Ride Z scheduled at 11:00 AM — ACTION REQUIRED
         ⚠️  Driver A cancelled Ride B; re-assignment in progress
     • Critical alerts (no driver found) displayed as dismissible banners at the top.
     • Each failure alert links directly to the ride detail page with a one-click
       "Emergency Assign" action.

  4. LIVE METRICS SUMMARY (TOP OF DASHBOARD)
     • Today's rides: Total | Confirmed | In Progress | Completed | Cancelled.
     • Assignment success rate for the day (%).
     • Average assignment lead time (minutes before scheduledAt the driver was assigned).
     • Drivers on shift now vs. total fleet size.

  5. UPCOMING RIDES (NEXT 24 HOURS)
     • Same table as Today's panel but filtered to rides in the next 24 hours.
     • Highlights rides whose assignment window opens within the next 30 minutes
       (so operators can pre-emptively monitor).

TECHNICAL IMPLEMENTATION

  Backend
  • New admin endpoint: GET /admin/operations/dashboard
    Returns: today's rides (with rider relation), driver statuses, alert counts.
  • Use Prisma queries with date range filters; leverage the existing
    @@index([status, createdAt]) and the new @@index([riderId, scheduledAt, estimatedEndTime]).
  • Real-time updates via the existing NotificationsGateway WebSocket:
    broadcast ride status changes to an "admin:operations" room so the dashboard
    auto-refreshes without polling.

  Frontend (Admin Panel)
  • Use the existing admin panel framework; add an "Operations" route.
  • The driver timeline view can be implemented with a lightweight timeline library
    (e.g., Timeline.js or a custom CSS grid — no heavy dependency needed).
  • Auto-refresh: subscribe to the "admin:operations" WebSocket room; update the
    relevant panel on each event (no full page reload).
  • Mobile-responsive: dispatchers may use tablets in the field.

RECOMMENDATIONS
  • Prioritise the Operations Dashboard alongside (or before) the public scheduling
    feature — it is the operational safety net that makes automation trustworthy.
  • Surface the "no driver found" alert prominently (e.g., a badge on the nav icon)
    so it cannot be missed even when the operator is on a different page.
  • Export buttons: allow dispatch to download today's ride manifest as CSV or PDF
    for offline reference or handover to the next shift.
  • Log every manual action taken from the dashboard (who assigned whom, when) —
    use the existing audit-log pattern in the backend for accountability.
